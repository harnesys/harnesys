# Отклонения от APPS_PLAN

`docs/APPS_PLAN.md` — источник истины. Этот файл фиксирует, где реализация отличается
от него и почему. Сам план не менялся.

## Бэкенд

1. **Egress проверяет hostname, а не закреплённый IP.** `provider-http.adapter.ts` резолвит
   hostname в рамках `EgressPolicy` и блокирует приватные диапазоны до запроса, но сам запрос
   затем отправляется по hostname. Смена DNS-ответа между проверкой и соединением не
   контролируется. Причина: у `fetch` в Bun нет поддерживаемого хука connect-по-IP без
   собственного диспетчера; закрепление добавило бы транспортную зависимость, которой нет в
   плане. Компромисс: окно сужено, но не закрыто.
2. **Маршруты вебхуков — явные обработчики методов.** `apps-hook.controller.ts` объявляет
   `POST`, `GET`, `PUT`, `PATCH` и `DELETE` для обоих уровней цели вместо одного маршрута
   `ANY`, потому что роутер brix не имеет декоратора `ANY`. Пути — в точности из плана; прочие
   методы возвращают 404.
3. **Настройка App получает `webhookUrl: null`.** У нового App нет id до создания, поэтому
   контекст настройки не может построить `…/apps/<appId>`. Манифест GitHub поэтому не включает
   `hook_attributes`. Провайдеры, которым нужен URL вебхука при настройке, должны получать его
   после создания; вью App показывает итоговый URL.
4. **Генерируемые поля материализуются в начале сессии.** `resolveInputs` заполняет поля с
   `generated: true` случайным токеном до запуска обработчика провайдера. Без этого
   генерируемый Telegram `secretToken` никогда бы не дошёл до `connect`/`directConnect`.
   Значение сохраняется только после завершения подключения.
5. **`ConnectSessionStorePort` получил `watch()`.** Порт расширен аддитивно, чтобы SSE-контроллер
   мог подписаться на изменения сессии; стор в памяти, поэтому подписка живёт в пределах
   процесса. Первый кадр SSE — полный снимок сессии, что делает безопасным переподключение
   `EventSource`.
6. **`ConnectSession` получил `launchFormHosts`.** Одноразовой HTML-странице запуска нужен явный
   allowlist `form-action` в её CSP. Хосты приходят из `Launch.html` провайдера, поэтому они
   хранятся в сессии, а не захардкожены в контроллере.
7. **Вебхуки аккаунта читают объединение секретных ключей app и аккаунта.** `handle-webhook`
   строит читалку секретов аккаунта из `[...accountKind.secrets, ...appKind.secrets]`. Область
   видимости по-прежнему задаётся префиксом `app:`/`account:` в scoped-сторе, поэтому
   дополнительные ключи не могут прочитать чужую запись. Причина: провайдеры вроде GitHub
   подписывают payload на уровне App секретом App, хотя хук доставляется на путь Аккаунта.
8. **Таблицы T1 пересоздаются.** `org-sql-apps.ts` дропает `app_accounts` и `apps`, если найдена
   старая схема T1 (без `metadata_json`). Данные T1 не мигрируются. Это следует предположению 4
   плана.
9. **Область конверта ошибок.** Новые маршруты возвращают `{ error, fields?, holders? }` для
   `AppsException`. Ошибки гардов (`401`/`403`) и Zod-валидация body/query сохраняют базовый
   контракт `ErrorResponse`. Причина: план задаёт новый формат, а не замену глобального фильтра.
10. **Удаление секретов.** `PATCH /apps/:appId` принимает `secrets: { key: null }`. Опциональные
    секреты удаляются; удаление обязательного секрета даёт `422 invalid_fields` с `required`.
11. **Правки аккаунта ограничены дескриптором.** `PATCH /accounts/:accountId` принимает только
    `label` и несекретные поля с пометкой `editable`. Прочие ключи отклоняются; секреты через
    этот маршрут не редактируются.
12. **Пикеры мультивидовых аккаунтов фильтруют на клиенте.** `GET /accounts` поддерживает один
    `kind` плюс `scopes`. `AccountPicker` принимает несколько видов и поэтому грузит список
    аккаунтов организации и фильтрует пригодность локально. Серверный фильтр остаётся
    источником истины для вызовов с одним видом.
13. **Каталог ограничен организацией.** `GET /orgs/:orgId/apps/catalog` стоит за
    `OrgAccessGuard`, как и любой другой приватный маршрут, вместо дампа глобального реестра.

## Фронтенд

1. **Консолидация файлов UI.** `ProviderCard` рендерит провайдера, его App'ы и его Аккаунты в
   одном компоненте вместо отдельных `AppList`/`AccountList`; `FieldRenderer` содержит
   замкнутый набор контролов полей в одном файле. Публичный API остаётся `AppsPane` и
   `AccountPicker` из `features/manage-apps`.
2. **Эндпоинты появляются после создания.** `EndpointsHelp` рендерится на сохранённых App'ах.
   Шаг App в визарде вместо этого показывает заметку, потому что redirect URI и URL вебхука
   содержат id App.
3. **Окно запуска и фолбэк.** Запуск `redirect`/`page` открывается один раз через
   `window.open`; `LaunchPanel` всегда держит обычную ссылку для браузеров с блокировкой
   попапов.
4. **Подтверждение удаления использует общий Dialog**, а не `window.confirm` (`noAlert`).
5. **Нет литералов провайдеров.** UI читает метки, поля, скоупы, иконки и справку из каталога.
   Запланированный скрипт `check-no-provider-names` и сгенерированный фиксчур не добавлены;
   юнит-спека покрывает `planConnect`, `connectReducer` и `buildValidator` на синтетическом
   дескрипторе.
6. **Секреты вида App в настройке.** Кнопка автоматической настройки отправляет и
   несекретные значения, и введённые секреты через `connect/start.inputs`, потому что контекст
   настройки раскрывает только `inputs`. Ручное создание сохраняет `values` и `secrets`
   раздельно.
7. **Поведение переподключения.** Переподключение открывает тот же визард с
   `target: 'account'`, существующим `accountId` и выданными скоупами под замком;
   `planConnect` возвращает только шаг `connect`.

## Верификация

- `bun run lint`: 0 ошибок, 12 предупреждений (контроллеры с более чем пятью параметрами).
- `bunx tsc --noEmit`: server, webui и contracts проходят.
- `bun test`: 1912 прошло, 0 упало на 380 файлах; новая спека модели добавляет 8 из них.
- Изолированный бут: `SERVER_PORT=47999 DEV_HARNEYSYS_HOME=$(mktemp -d) bun src/main.ts`
   достигла `[server listening] port=47999`, `/health/live` вернул 200, процесс остановлен
   после проверки. Все маршруты apps, accounts, connect, callback, launch и hook
   смаппированы.
- `git diff` для каждого пути из §14.1 пуст.

## Не покрыто

- Закрепление IP для egress.
- Автоматическая регистрация/ротация вебхуков на стороне провайдера (Telegram `setWebhook`,
   хук манифеста GitHub). URL раскрыты, но регистрация остаётся шагом оператора.
- CI-гейты/скрипты из §14.3 (`check-no-provider-names`, проверка дрифта фиксчура) отсутствуют;
   UI на каталоге и спека модели покрывают тот же замысел по построению.
- Отдельные серверные юнит-спеки для валидации полей, маппинга статусов и соответствия
   провайдеров в этом проходе не добавлены; фронтендовая спека модели покрывает только
   `planConnect`, редьюсер и `buildValidator`.
