# Что такое аддоны и зачем они нужны

## Проблема, которую решает платформа

Ядро Harnesys — платформа агентов: треды, запуски, автоматизации, паки инструментов, учётные записи. Продукту нужно расти быстрее, чем меняется ядро: подключать GitHub, Google, Telegram, планировщики, вебхуки — не превращая каждое подключение в правку ядра. Классические системы плагинов при этом наступают на грабли:

| Грабли известных систем | Решение в Harnesys |
|---|---|
| Общий процесс расширений: одно зависшее расширение тормозит все (VS Code) | процесс на пару (организация × аддон), дедлайны, квоты, watchdog, ping-надзор |
| У плагина фактически права пользователя; in-process видит всё | прав нет по умолчанию: каждый вызов хоста проходит проверку `декларация ∩ грант ∩ политика`; `restricted`-профиль — OS-песочница |
| Обновление тихо расширяет права (уроки Chrome/Android) | версия закреплена за организацией; новые обязательные права → состояние `needs_consent`, молча не применяется |
| Все плагины активируются на старте и тормозят запуск | активация ленивая: код стартует только при первом использовании; вклады — данные, реестры читают их без исполнения кода |
| Динамическая регистрация и утечки при выгрузке | вклады статические из манифеста; каждая регистрация принадлежит `OwnerKey` и обязана `dispose()`; тест «реестры после `deactivate` равны исходным» |
| Совместимость по номеру сборки ломается каждый релиз | один целочисленный `platform` + рукопожатие с возможностями; неизвестные поля терпимы; удаление семантики — только новый мажор |
| Плагины зависят друг от друга кодом | зависимостей аддон → аддон нет: только события, вклады и connections |
| UI плагинов — код внутри приложения | декларативные секции ядра + изолированный `frame`; код аддона в UI хоста не исполняется никогда |

## Модель в трёх абзацах

**Пакет** — каталог с манифестом `addon.json` и самодостаточным JS-бандлом. Манифест статически описывает: что аддон даёт (`contributions` — вклады в 13 семейств), что ему нужно (`permissions`, `connections`), как его запускать (`runtime.profile`, `activation`) и где его данные (`data.migrations`, `quotaMb`).

**Хост** — ядро сервера. Считает пакеты в каталог (`addons.lock.json` + версии на диске), включает аддон организации с явной выдачей прав, регистрирует вклады в реестрах ядра **как данные, не запуская код**, и по требованию поднимает изолированный процесс аддона. Общение — JSON-RPC 2.0 по stdio: хост вызывает обработчики (`tools.call`, `route.handle`, …), аддон — сервисы хоста (`db.*`, `http.fetch`, …). Каждая точка входа проверяет право, схему, частоту, дедлайн; наружу из процесса идут только коды ошибок.

**Автор аддона** пишет `defineAddon({ tools, routes, triggers, jobs, workers, hooks, transport, sources, lifecycle, notifications })` и пользуется контекстом `ctx` — типизированным клиентом хост-сервисов из `@harnesys/sdk`. Локально всё это гоняется на fake-хосте из `@harnesys/sdk/testing` без установленного Harnesys.

## Что аддон умеет — короткий список возможностей

- **Инструменты для агентов** — паки (`tool-pack`) с JSON-Schema входа, эффектами `read/write/destructive`, идемпотентностью; ядро назначает паки агентам и ведёт согласования.
- **Триггеры автоматизаций** — свои виды триггеров (`trigger`), экземпляры настраивает пользователь, запуск дедуплицируется и лимитируется хостом.
- **Расписания** — `job` (cron / каждые N секунд, catch-up) и `worker` (фоновая активность с autostart, restart и durable-лизингом).
- **HTTP-маршруты** — `route` под org-API (`/r/*`) с ролями member/admin и публичные endpoints (вебхуки).
- **Чат-транспорт** — `transport`: полноценный мост внешнего мессенджера в треды, с исходящим стримингом ответов (host-side projection), typing, вложениями и HITL-вопросами.
- **Облачные источники знаний** — `source-kind`: папка на Drive как знание-источник с зеркалением ядром.
- **Скиллы и промпты** — `content`: файлы пакета регистрируются как скиллы организации.
- **Конфиг и UI** — `config` (декларативные поля формы с секретами, условной видимостью, виджетами) и `view` (секции страницы аддона: таблицы, формы, действия, markdown, frame).
- **События** — emit в шину организации, хуки `hook` на события ядра (`thread.created`, `run.finished`, …) и на события провайдера.
- **Данные** — собственная SQLite на организацию с миграциями и квотой; файлы workspace; секреты в vault хоста.
- **Агенты** — диспатч запусков, создание тредов, компакция, запросы к usage/skills/org-настройкам, создание HITL-согласований.

## Границы: чего платформа не делает

- Не хранит учётные данные провайдеров и не проводит OAuth — это слой **Apps/Accounts**; аддон лишь объявляет потребности (`connections`) и получает привязанные аккаунты.
- Не исполняет код аддона в UI и не даёт ad-hoc произвольных точек расширения: только зарегистрированные семейства и сервисы.
- Не имеет маркетплейса и подписи пакетов: слоты заложены, внешние источники выключены до появления верификации подписей ([перспектива](roadmap.md)).
- Не запускает скрипты установки (`postinstall` запрещён): сборка — дело автора, установка — копирование проверенных файлов.

## Инварианты платформы

Нарушение любого — отказ на ревью независимо от зелёных тестов:

1. Аддон импортирует только `@harnesys/sdk`; SDK не импортирует ядро; ядро не импортирует аддоны.
2. Ядро не знает имён аддонов и не ветвится по семейству/методу — диспетчеры табличные.
3. Вклады статические: объявлены в манифесте, регистрируются без запуска кода.
4. Активация ленивая: на старте сервера код аддонов не исполняется.
5. Нет ambient authority: всё сверх базового набора — через право; эффективный доступ = декларация ∩ грант ∩ политика.
6. Изоляция: процесс на (организация × аддон); чужих данных и процессов не видно.
7. Каждая регистрация имеет владельца и `dispose`; после выключения — ноль процессов, регистраций, таймеров, подписок.
8. Секреты провайдеров не уходят аддону по умолчанию (токен можно вообще не отдавать — инъекция в `http.fetch`).
9. Обновление с расширением прав не применяется молча.
10. Контракт растёт аддитивно; слом семантики — новый `platform`.
11. Наружу идут коды `AddonErrorReason`, а не тексты исключений.
12. Fail-closed: неизвестный platform/семейство, битый манифест, дрейф digest — отказ.

## Экосистема уже в поставке

Тринадцать встроенных аддонов в `add-ons/` — не демо, а рабочие части продукта:

| Аддон | Что демонстрирует |
|---|---|
| `harnesys.webhook` | минимальный аддон: trigger + public route + view-таблица |
| `harnesys.scheduler` | cron-планировщик на job+trigger, org timezone, HITL-эскалация пропусков |
| `harnesys.telegram-bot` | транспорт чата: transport + worker-поллер + 12 tool-ов + привязка чатов + исходящие вложения |
| `harnesys.telegram-feed` | MTProto-аккаунт как connection (`telegram-user`), чтение каналов в треды |
| `harnesys.telegram-groups` | бот-транспорт для групп (connection `telegram-bot`), привязка чатов, tools |
| `harnesys.github` | GitHub App: installation-аккаунты, пака tools (21 инструмент), события через опрос (worker-poller + trigger `github.repo`) |
| `harnesys.google-*` (7) | tool-pack поверх OAuth-аккаунтов; `google-drive` — `source-kind` (облачный диск как знания) |

Разбор `harnesys.webhook` построчно — в [Анатомии аддона](anatomy.md).
