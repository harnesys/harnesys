# 01. Карта распределения функций (Core vs Add-ons Matrix)

**Статус:** Черновик для архитектурного ревью  
**Цель:** Быстрый поиск ответа на вопрос «Где должен находиться этот функционал?»

## 1. Матрица функциональных границ

### 1.1 Однозначное ядро: контрольная панель (Control Plane)
Эти области никогда не становятся аддонами.

| Текущая область | Целевой владелец | Примечания |
|---|---|---|
| Организации, идентификация, членство, приглашения | Ядро | Авторитет по тенентам и авторизации |
| Определения агентов и исполнение графов | Ядро | Корректность runtime |
| Потоки, сообщения, запуски, сжатие, бюджет | Ядро | Инвариант продукта |
| Апрувы, HITL, права доступа | Ядро | Политика и соблюдение |
| Хранилище секретов | Ядро | Аддоны хранят ссылки/права, а не сами секреты |
| Флот, протокол relay/worker, размещение, аренда | Ядро | Субстрат исполнения |
| Резолвер возможностей и реестр инструментов | Ядро | Единый реестр для встроенных и сторонних инструментов |
| Шина событий, модели чтения, SSE/WebSocket | Ядро | Единая проекция и backbone в реальном времени |
| Платформа аддонов и супервизор | Ядро | Не может быть аддоном |
| Аудит и учет использования | Ядро | Должно видеть все опосредованные операции |

### 1.2 Движки ядра с опциональными провайдерами
Ядро владеет нейтральным механизмом (движком), а конкретные реализации (ресурсные провайдеры или провайдеры сервисов) выносятся в аддоны.

| Текущая область | Ядро сохраняет (Движок) | Кандидат в аддон (Провайдер) |
|---|---|---|
| Источники и материализация | Модель источников, оркестрация, доступность, политика файлов | Git, Google Drive и будущие бэкенды источников |
| Транспорт чатов | Маршрутизация потоков, политика эха/агентов, HITL-мост | Telegram и будущие транспорты |
| Диспетчеризация триггеров | Идентификация триггера, состояние срока, цель, повторы | Типы триггеров с конфигурацией на стороне провайдера |
| MCP | Реестр, обнаружение, права, жизненный цикл | _(Аддоны могут поставлять MCP-серверы как вклады)_ |
| LSP | Реестр, транспорт диагностики, жизненный цикл | _(Аддоны могут поставлять LSP-серверы как вклады)_ |
| Знания/память | Модель данных, политика поиска, права доступа | Реализации бэкендов поиска и индексации |
| Терминалы/файлы | Протокол сессии, политика доступа, транспорт | Специализированные редакторы и инструменты работы с файлами |

### 1.3 Однозначное владение аддонами
Функционал, который должен быть полностью вынесен из ядра.

| Текущая область | Целевой владелец | Примечания по экстракции |
|---|---|---|
| Telegram: подключение, поллинг, транспорт, данные | Аддон Telegram | Ядро сохраняет нейтральный мост сообщений |
| Google: OAuth, Drive, Gmail, Calendar, YouTube и др. | Аддон Google | Ядро сохраняет движки источников и сообщений |
| GitHub: App, connectivity, операции API | Аддон GitHub | Ядро сохраняет общие движки задач и источников |
| Специфичные наборы инструментов провайдеров | Провайдер-аддон | Ядро сохраняет реестр, политику и диспетчеризацию инструментов |
| Профили инструментов браузера/web | Аддон браузера/web | Политика процессов и сети остается под контролем хоста |
| Интерфейсы инструментов shell/files | Аддон shell/files | Политика файлов и исполнение воркеров остаются под контролем ядра |
| Скиллы, промпты, команды, пресеты агентов | Контент-аддон | Ядро сохраняет репозитории контента и семантику выбора |
| Подписки на хуки как устанавливаемый пакет | Вклад аддона | Ядро сохраняет шину событий и разрешенные эффекты |
| Пакеты MCP-серверов | Вклад аддона | Ядро сохраняет жизненный цикл MCP |
| Страницы настроек, формы, карточки, статусы аддона | Аддон | Ядро предоставляет декларативную оболочку и доставку ресурсов |
| HTTP-маршруты, колбэки и фоновые воркеры аддона | Аддон | Ядро предоставляет изолированную маршрутизацию и супервизию |

### 1.4 Кандидаты в модули продукта (Требуют разделения домена)
Эти модули переносятся только после того, как их зависимости от ядра будут полностью изолированы.

| Кандидат | Целевой владелец | Причина переноса | Блокирующее условие |
|---|---|---|---|
| Доска задач и правила задач | Аддон доски задач | Опциональное планирование | Разделение семантики досок, вложений и правил с ядром |
| Автоматизация браузера | Аддон браузера | Опциональный инструмент | Запуск ядра не должен зависеть от наличия браузера |
| Shell/files как продукт | Аддон shell/files | Возможность агентов без исполнения кода | Возможность отключения доступа к файлам без потери гарантий |
| Реализация знаний/поиска | Аддон знаний | Опциональный провайдер поиска | Явные инварианты владения памятью в ядре |
| LSP как опциональный модуль | Аддон LSP | Опциональный инструмент разработчика | Грациозная деградация UX при отсутствии LSP |
| Адаптеры провайдеров моделей | Провайдер-аддон | Экосистема моделей | Требуется отдельный ADR по архитектуре драйверов |

## 4. Сосуществование с легаси

Платформа аддонов и текущие механизмы ядра сосуществуют в период миграции:

- **Новые швы аддонов** не переиспользуют legacy швы напрямую; для их создания допускается легкая модификация ядра (Фаза 2) без изменения видимого поведения runtime.
- **Текущие механизмы** продолжают работать без изменений, пока соответствующий функционал не будет перенесен в аддон.
- **Миграция** происходит функцией за функцией через поэтапное переключение (feature switch) с сохранением одного авторитетного записьщика, после чего старая реализация удаляется.
