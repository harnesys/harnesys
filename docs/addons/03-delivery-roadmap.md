# 03. Дорожная карта внедрения (Delivery Roadmap)

**Статус:** Черновик для архитектурного ревью  
**Целевая аудитория:** Проджект-менеджеры, техлиды, команда разработки

Этот документ определяет последовательность этапов, временные рамки и ключевые результаты процесса перехода на платформу аддонов.

## 1. Потоки работ (Workstreams)

Для параллельного продвижения по фазам выделены следующие потоки работ:

| ID | Поток работ | Результат |
|---|---|---|
| **W1** | Инвентаризация функций и карта владения | Каждый текущий функционал имеет целевого владельца и класс миграции |
| **W2** | Целевая архитектура и ADR | Утвержденные контракты для границ, runtime, прав, данных, триггеров, UI и версий |
| **W3** | Подготовка ядра | Описанное поведение и создание общих точек сопряжения (seams) без поломки текущей работы |
| **W4** | Фундамент платформы | Единый управляемый хостом жизненный цикл аддонов (установка, права, процессы, данные) |
| **W5** | Эталонные аддоны и пилотная миграция | Сквозное доказательство работы на аддонах, близких к продакшн-решениям |
| **W6** | Прогрессивная экстракция | Перенос остальных опциональных функций без двойного владения |
| **W7** | Удаление легаси | Полное удаление временных адаптеров, реестров и схем после верификации миграции |

## 2. Последовательность Фаз

Реализация идет итерациями. Переход к следующей фазе возможен только после закрытия «критерия выхода» (Exit Gate).

### Фаза 0: Инвентаризация и база решений
**Цель**: Создать полную карту продукта без изменения поведения runtime.
- **Действия**: Инвентаризация REST, WebUI, фоновых задач и таблиц; классификация по классам владения (K, E, A, M, X, R); поиск всех литералов ресурсных и сервисных провайдеров в коде.
- **Результат**: Матрица владения и карта специализаций провайдеров.
- **Критерий выхода**: Каждый workflow имеет владельца; определена судьба всех литералов схем ядра.

### Фаза 1: Утверждение целевой архитектуры
**Цель**: Согласовать минимальный набор контрактов на ближайшие 5 лет.
- **Действия**: Принятие списка ADR (см. раздел 3); определение формы контрактов для идентификации, прав, жизненного цикла и хранения данных.
- **Критерий выхода**: Все ADR приняты; утвержден состав модулей (включая статус доски задач).

### Фаза 2: Подготовка ядра
**Цель**: Подготовить приложение к платформе без изменения поведения, видимого пользователю.
- **Действия**: Создание общих портов и схем; подготовка замены литералов провайдеров (с сохранением текущих); разделение адаптеров и нейтральных движков; выделение провайдера эмбеддингов (`StudioEmbeddings`) и sqlite-векторного поиска (`knowledge-search.ts`) за нейтральные движковые порты с текущими адаптерами по умолчанию; перевод параметров чанкинга (`chunk-text.ts`) в настройки ядра; вынесение семантики нотификаций в нейтральный движок (события, дедупликация, дефолтный канал `desk` поверх SSE — без изменения видимого поведения).
- **Критерий выхода**: Тесты и запуск проходят успешно; границы движков/адаптеров определены в коде.

### Фаза 3: Фундамент платформы
**Цель**: Построить платформу для хостинга декларативных и исполняемых аддонов.
- **Действия**: Реализация манифеста, каталога, системы прав, изоляции данных, супервизора процессов и базовых сервисов хоста.
- **Критерий выхода**: Минимальный аддон проходит полный цикл (установка $\rightarrow$ работа $\rightarrow$ удаление); запуск ядра не зависит от аддонов.

### Фаза 4: Пилотное внедрение (Эталонные аддоны)
**Цель**: Проверить платформу на ограниченном наборе реальных сценариев.
- **Действия**: Реализация эталонов (контент-аддон, провайдер-аддон, триггер-аддон, пилотный продуктовый модуль).
- **Критерий выхода**: Все эталоны работают корректно; права доступа не обходятся; команда может создать новый аддон по контракту.

### Фаза 5: Волны прогрессивной экстракции
**Цель**: Перенос основного функционала контролируемыми волнами.

| Волна | Типичный контент | Условие входа | Условие выхода |
|---|---|---|---|
| **1** | Слабосвязанный контент и возможности провайдеров | Границы ядра общие | Нет параллельного владения |
| **2** | Интеграции провайдеров и наборы инструментов | Контракт инструментов стабилен | Данные и UI живут в аддоне |
| **3** | Провайдеры триггеров и автоматизация | Движок триггеров стабилен | Один путь диспетчеризации |
| **4** | Опциональные модули с существенным UI/данными | Мост взаимодействия ядра стабилен | Полное владение модулем |
| **5** | Сильносвязанные домены (после разделения) | Точки сопряжения доказаны | Один источник истины |

### Фаза 6: Сосуществование с легаси
**Цель**: Обеспечить работу продукта в период перехода.
- **Правила**: Один авторитетный записьщик на домен; временная двойная запись только при миграции данных; использование адаптеров совместимости.

### Фаза 7: Очистка и завершение
**Цель**: Удалить всю инфраструктуру миграции.
- **Действия**: Удаление легаси-реестров, таблиц, маршрутов и флагов переключателей.
- **Критерий выхода**: Grep-проверки чистоты кода проходят; продукт проходит все тесты и запуск в продакшн-среде.

## 3. Перечень ключевых архитектурных решений (ADR)

Эти решения должны быть приняты в Фазе 1:

- **ADR-01**: Владение (Ядро против Аддонов).
- **ADR-02**: Модель расширения (Манифест, Жизненный цикл).
- **ADR-03**: Изоляция исполняемого кода (Песочница).
- **ADR-04**: Модель прав доступа (Capability-based).
- **ADR-05**: Владение данными и изоляция хранилищ.
- **ADR-06**: Модель триггеров (Диспетчеризация $\rightarrow$ Определение).
- **ADR-07**: Модель UI (Оболочка $\rightarrow$ Вклады).
- **ADR-08**: Стратегия совместимости и версионирования.
- **ADR-09**: Модель распространения (Локальная установка $\rightarrow$ Дистрибуция).
- **ADR-10**: Механизм миграции и правила удаления совместимости.
- **ADR-11**: Модель нотификаций (движок ядра владеет событиями, дедупликацией и приоритетами; каналы доставки — вклады в `notification-channel`).
- **ADR-12**: Провайдеры эмбеддингов и бэкенды поиска знаний (эмбеддинг-модели — вклад в `model-provider`, хранилища/поиск — вклад в `search-backend`).
- **ADR-13**: Экспорт телеметрии (read-only проекция usage/latency ядра; экспортеры — вклады в `telemetry-exporter`).
- **ADR-14**: Архитектура драйверов провайдеров моделей (LLM-адаптеры как вклады в `model-provider`; ядро владеет реестром моделей, политикой выбора и бюджетами; драйвер-аддон владеет протоколом доступа к API провайдера).
