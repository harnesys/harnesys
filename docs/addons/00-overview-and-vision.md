# 00. Обзор и видение платформы аддонов

**Статус:** Черновик для архитектурного ревью  
**Целевая аудитория:** Менеджеры, разработчики, архитекторы

## 1. Суть и цели

Платформа аддонов призвана превратить монолитное приложение в расширяемую систему, где базовый функционал отделен от опциональных возможностей.

**Главная цель**: Позволить пользователям устанавливать только необходимые им возможности, а разработчикам — поставлять новые функции и интеграции без необходимости переписывать или форкать ядро продукта.

**Конвергенция каналов**: Платформа объединяет разрозненные ранее механизмы распространения (паки, плагины и интеграции) в единый стандарт аддонов, обеспечивая согласованный жизненный цикл установки, обновления и управления правами.

### Что НЕ является целью (Non-goals)
- Создание публичного маркетплейса или коммерческой политики дистрибуции на начальном этапе.
- Обеспечение абсолютной изоляции каждого аддона на уровне ядра (песочница зависит от класса прав).
- Вынос каждой функции из ядра только ради увеличения количества аддонов.
- Поддержка встраивания аддонов в ядро: ядро не импортирует код аддона, не вызывает его по имени, функции или методу и не ветвится по идентификатору аддона (например, `if (addonId === ...)`). Подключение аддона выполняется только через семейства контрактов и разрешение по типу порта.

## 2. Архитектурные принципы

Система строится на четырех фундаментальных правилах:

1. **Ядро владеет семантикой и политиками.** Оно отвечает за идентификацию, права доступа, секреты, жизненный цикл агента/запуска, диспетчеризацию триггеров, разрешение прав и аудит.
2. **Аддоны владеют опциональными реализациями и представлением.** Они отвечают за поведение провайдеров ресурсов или сервисов, опциональные функции продукта, предоставляемые инструменты/контент, данные аддона и создаваемый ими UI.
3. **Расширение без ветвлений в ядре.** Новый провайдер, функция или источник данных не требует добавления новых литералов в объединения (unions) ядра, новых маршрутов ядра, новых ветвлений в UI ядра или знания об аддоне по имени.
4. **Платформа аддонов строится на подготовленной системе.** Ядро сначала приводится в состояние, которое само поддается расширению: в каждой намеченной точке расширения ядро владеет нейтральным механизмом и открытым швом, без изменения видимого поведения (Фаза 2). Сами швы аддонов проектируются заново и не повторяют огрехи текущих (legacy) швов; легаси используется только как инвентарь фактов. Модификации ядра выполняются до начала разработки платформы и принимаются только после прохождения регрессионных тестов — до написания первого аддона.

## 3. Принцип границы

Граница между ядром и аддоном проводится по **семантическому владению**, а не по объему кода.

> **Ядро** владеет инвариантами продукта, корректностью исполнения, политиками и их соблюдением.  
> **Аддоны** владеют опциональными реализациями, поведением провайдеров, предоставляемыми возможностями, собственными данными и собственным представлением.

**Условие переноса функции в аддон:**
Функция становится аддоном только если её можно отключить без поломки ядра, её поведение доступно через сервисы хоста, данные изолированы, права декларируемы независимо, а удаление не затрагивает инварианты ядра.

## 4. Установка и исполнение аддона

**Единица установки.** Аддон поставляется бандлом: манифест `addon.json` (идентификатор, версия, семейства вкладов, запрашиваемые права, режим исполнения) плюс код и ресурсы. Хост копирует бандл в `orgDataDir/addons/<id>/<version>/`, пишет запись в каталог и материализует запрашиваемые права в неизменяемый набор предоставленных прав (`grant set`). Любое расширение прав в новой версии требует повторного согласия администратора.

**Регистрация вкладов.** Супервизор загружает аддон универсальным загрузчиком, читает семейства вкладов из манифеста и регистрирует их в реестрах ядра как обычные записи. Ядро не содержит ни имени, ни пути, ни импорта конкретного аддона; вклад встроенного механизма и вклад аддона различимы только по источнику.

**Режимы исполнения.** Код аддона выполняется в одном из двух режимов, объявленных в манифесте:

| Режим | Где выполняется | Свойства |
|---|---|---|
| **Процессный** | Отдельный процесс под супервизором хоста | Изоляция сбоя и бюджета; обмен сообщениями через IPC |
| **В процессе** | Загруженный модуль в адресном пространстве ядра | Быстрые вызовы; изоляция только на уровне границы SDK, без доступа к DI-контейнеру и внутренним импортам ядра |

Порядок внедрения: процессный режим первым, в процессе — вторым. Все сервисы хоста спроектированы как удалённые (без замыканий, общих ссылок и сигналов как параметров; отмена — по идентификатору операции), поэтому второй режим становится прямым вызовом, а первый — маршалингом тех же сообщений, без переделки API.

**Удаление.** Супервизор останавливает аддон, снимает вклады с реестров и удаляет запись каталога. Удаление данных аддона требует отдельного согласия.

## 5. Классы владения

Для определения места функционала используются следующие классы. Классы применяются к областям кода ядра, а не к аддонам: аддон — это единица установки с набором вкладов и декларацией прав, которая может владеть как опциональным вкладом, так и собственным доменом (данные, UI, состояние).

| Класс | Значение | Где располагается |
|---|---|---|
| **K — Инвариант ядра** | Корректность продукта, безопасность, тенентность, семантика runtime | Только в Ядре |
| **E — Движок ядра** | Нейтральный механизм без привязки к конкретному провайдеру | В Ядре (провайдеры могут быть аддонами) |
| **A — Вклад аддона** | Опциональная возможность без владения продуктовым доменом | В Аддоне |
| **X — Адаптер миграции** | Временный путь совместимости при экстракции | Временно (удаляется после миграции) |
| **R — Резервный шов** | Запланированная точка расширения на будущее | Описана в архитектуре $\rightarrow$ Реализована позже |
