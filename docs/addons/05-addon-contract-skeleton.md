# 05. Скелет контракта аддона (Addon Contract Skeleton)

**Статус:** Черновик для архитектурного ревью
**Целевая аудитория:** Дизайнеры ядра; основа для составления плана Фазы 2

## 1. Назначение и границы

Это скелет, а не полный контракт: фиксирует лексику, на которой выводится
подготовка ядра, и не «покупает» семантику, требующую собственных ADR.

Здесь решено: идентификация аддона, форма вклада, состав host-сервисов,
формат прав. Сознательно не решено — раздел 6. Весь объем, блокирующий
Фазу 2, помещается в разделы 2–4.

## 2. Идентификация

| Сущность | Поле | Правило |
|---|---|---|
| Аддон | `addonId` | kebab-case slug, глобально уникален, неизменяем после установки |
| Аддон | `version` | semver; в рамках мажорной версии — additive-only (02 §1.3) |
| Вклад | `contributionId` | уникален в паре `addonId + family`; аддоны не перезаписывают вклады друг друга молча (02 §1.3) |

Идентификаторы — строки, а не литералы ядра: в ядре нет закрытого списка
допустимых `addonId` и `kind` вкладов.

## 3. Вклад (Contribution)

Вклад — декларативная запись, распознаваемая ядром по семейству:

```
Contribution {
  addonId, version
  family        // 'tool' | 'context' | 'content' | 'hook' | 'mcp' | 'lsp'
                // | 'trigger' | 'route' | 'worker' | 'view' | ...
  id            // contributionId
  descriptor    // форма, своя для каждого семейства
  capabilities  // запрашиваемые права domain:action
}
```

- Список семейств и владельцев исполнения — 02 §1.1; он устойчив и
  расширяется только через ADR.
- Ядро проверяет структуру вклада и совместимость версии платформы;
  семантику descriptor'а определяет семейство, его статус стабильности
  указан в 02.
- Вклады регистрируются в едином реестре; в UI ядра запрещены ветки
  вида `if (addonId === ...)` (02 §4.2).

## 4. Host-сервисы (контекст аддона)

Аддон получает контекст через порт, а не через импорты ядра.

`AddonContext` — самостоятельный контракт, проектируемый заново: легаси не
наследуется и не оборачивается. Файл
`packages/harnesys/src/integration/types.ts` (`IntegrationContext`) — только
инвентарная ссылка: доказательство того, какой набор сервисов фактически
потребляла интеграция-предшественник. Состав
`db, secrets, logger, workers, automations, threads, runs, events, routes`
принят как факт потребности, но не как форма: легаси-типы в новый шов
не попадают.

Стартовые решения нового контракта:

| Элемент | Решение нового шва | Легаси-факт для сравнения |
|---|---|---|
| Секреты | только непрозрачные ссылки + резолвер по правам (02 §3.2) | `AddonSecrets.get/set` возвращают сырые значения (`addon-secrets.ts:15`) — дефект, не переносится |
| Имя и область видимости | `AddonContext`, нейтрален к доменам | `IntegrationContext` привязан к домену интеграций |
| Данные | собственный изолированный SQLite аддона; прямой доступ к базам ядра запрещен (02 §3.2) | то же решение |

Сервисы `logger`, `threads`, `runs`, `events`, `automations`, `routes`,
`workers` описываются в новом контракте собственными типами; их финальные
формы сверяются с легаси-фактами при ревью ADR-02.

Правило исполнения: каждый вызов сервиса проходит проверку эффективных
прав `(задекларировано ∩ предоставлено ∩ контекст организации)` — 02 §3.1.

## 5. Права

- Формат `domain:action`; каталог доменов и действий открыт и пополняется
  вместе с вкладами; в ядре нет enum'а прав.
- Манифест аддона декларирует список прав; хост хранит неизменяемый
  grant set на установленную версию; расширение прав при обновлении требует
  нового согласия. Детальная модель — 02 §3.1 (ADR-04).

## 6. Сознательно не решено в скелете

| Вопрос | Почему отложен | Куда |
|---|---|---|
| Чем технически исполняется аддон (in-process / воркер-процесс / песочница) | Определяет ADR-03 и супервизора, но не выводит рефакторинг Фазы 2 | ADR-03 |
| Флот: размещение резидентных аддонов по нодам | Отложено пользователем; первое приближение — десктоп/self-hosted | Отдельный ADR после Фазы 4 |
| UI-вклад (view, file-view, settings) | Не блокирует подготовку ядра | ADR-07; шов `view` остается резервным |
| Полная схема манифеста | Нужна к Фазе 3; скелет фиксирует только поля разделов 2–5 | ADR-02 |
| Версионирование и совместимость | Отдельное решение | ADR-08 |
