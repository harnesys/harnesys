# 02. Технический стандарт аддона (Contracts & Security)

**Статус:** Черновик для архитектурного ревью  
**Целевая аудитория:** Разработчики ядра и создатели аддонов

Этот документ определяет техническую спецификацию системы аддонов: как они устроены, как взаимодействуют с ядром и какие ограничения накладываются на их работу.

## 1. Модель точек расширения (Extension Points)

Платформа предоставляет набор семейств точек расширения. Каждый вклад в точку расширения должен быть задекларирован в манифесте аддона.

### 1.1 Основные точки расширения

| Семейство | Что предоставляет аддон | Владелец исполнения | Стабильность |
|---|---|---|---|
| `tool` | Схема инструмента и обработчик вызова | Аддон или сервис хоста | Стабильно |
| `context` | Фрагмент контекста с правилами области и порядка | Аддон | Стабильно |
| `content` | Скиллы, промпты, команды, пресеты агентов | Аддон или репозиторий ядра | Стабильно |
| `hook` | Подписка на событие ядра и разрешенный эффект | Шина событий ядра | Стабильно |
| `mcp` | Дескриптор MCP-сервера | Реестр MCP ядра | Стабильно |
| `lsp` | Дескриптор LSP-сервера | Реестр LSP ядра | Стабильно |
| `trigger` | Тип триггера и контракт конфигурации | Движок триггеров ядра + аддон | Экспериментально |
| `route` | HTTP-маршрут (аутентифицированный/публичный) | Роутер ядра + обработчик аддона | Стабильно |
| `worker` | Фоновая активность (lifecycle-bound) | Супервизор ядра | Стабильно |
| `view` | Декларативный или изолированный UI-вид | UI shell ядра | Смешанная |

### 1.2 Резервные швы (Reserved Seams)
Точки расширения, которые зафиксированы в архитектуре, но будут реализованы только после утверждения соответствующих ADR:
- `model-provider`: Сторонние провайдеры моделей/эмбеддингов (LLM Providers).
- `source-kind`: Сторонние ресурсные провайдеры источников (Resource Providers).
- `graph-action`: Кастомные операции графа.
- `workspace-widget`: Виджеты дашборда или редактора.
- `transport`: Дополнительные провайдеры транспортов сообщений (Service Providers).

### 1.3 Правила вкладов
1. **Валидация**: Ядро проверяет структуру и совместимость; аддон отвечает за доменную семантику.
2. **Отказоустойчивость**: Структурные дефекты или несовместимые версии блокируют установку аддона.
3. **Идентификация**: Используются именованные идентификаторы. Два аддона не могут молча перезаписывать вклад друг друга.
4. **Версионирование**: Стабильные контракты в рамках мажорной версии могут только расширяться (additive-only).

## 2. Модель исполнения (Execution Modes)

Режим исполнения — это свойство среды выполнения (runtime), определяющее, как выделяются ресурсы процесса.

| Режим | Поведение процесса | Примеры вкладов |
|---|---|---|
| **Инертный (Inert)** | Процесс не запускается; используются только данные/ресурсы | Декларативный контент, статические промпты |
| **По требованию (Demand)** | Процесс запускается только при вызове конкретной возможности | Инструменты, обработчики маршрутов, провайдеры контекста |
| **Резидентный (Resident)** | Долгоживущий процесс с постоянным присутствием в памяти | Поллеры, транспорты сообщений, синхронизаторы |

*Резидентные аддоны обязаны задекларировать причину своего присутствия и ограничены строгими бюджетами на память, CPU и количество перезапусков.*

## 3. Безопасность и доступ

### 3.1 Права доступа (Permissions)
Права используют формат `domain:action` (например, `threads:read`).

1. **Декларация**: Аддон запрашивает список прав в манифесте.
2. **Предоставление**: Хост хранит неизменяемый набор предоставленных прав (`grant set`) для установленной версии.
3. **Проверка**: Эффективный доступ = (Задекларировано $\cap$ Предоставлено $\cap$ Контекст организации).
4. **Принцип**: Отсутствие права означает запрет (Deny by default).
5. **Обновления**: Любое расширение прав в новой версии аддона требует повторного согласия пользователя/администратора.

### 3.2 Изоляция данных и секретов
- **Секреты**: Все секреты хранятся в Vault ядра. Аддоны владеют только непрозрачными ссылками на секреты и получают значение только при наличии прав.
- **Данные**: Каждый аддон владеет своим изолированным хранилищем. Прямой доступ к базе данных ядра запрещен.
- **Модели чтения (Read-models)**: Для UI создается единая аддитивная проекция состояния. Строка модели чтения является проекцией, а не дубликатом бизнес-данных аддона.

## 4. Специализированные модели

### 4.1 Модель триггеров
Разделение на механизм планирования (Ядро) и определение условий (Аддон).
- **Ядро**: Планирование, очередь, диспетчеризация, аудит, лимиты ресурсов.
- **Аддон**: Тип триггера, контракт конфигурации, валидация условий срабатывания.
- **Безопасность**: Провайдер триггера не имеет доступа к планировщику; все запущенные им действия проходят проверку прав доступа ядра.

### 4.2 Модель доставки ресурсов и UI
- **UI Shell**: Ядро владеет основной оболочкой.
- **Вклады**: Аддоны предоставляют декларативные данные или изолированные представления (views) через утвержденный API.
- **Разделение**: В UI ядра запрещены ветвления вида `if (addonId === ...)`. Все расширения должны быть дескриптивными.
