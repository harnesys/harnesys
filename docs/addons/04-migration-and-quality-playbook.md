# 04. Регламент миграции и контроля качества (Migration & Quality Playbook)

**Статус:** Черновик для архитектурного ревью  
**Целевая аудитория:** Разработчики, проводящие перенос функционала, и ревьюеры.

Этот документ является практическим руководством по безопасному переносу функционала из ядра в аддоны. Его цель — исключить регрессии и обеспечить атомарность перехода.

## 1. Алгоритм переноса функции (Шаг за шагом)

Каждый перенос функционала должен строго следовать данной последовательности:

1. **Фиксация контракта**: Описать текущее поведение функции с помощью тестов характеризации.
2. **Анализ зависимостей**: Выявить все нейтральные зависимости от ядра (сервисы хоста), которые потребуются аддону.
3. **Проектирование вклада**: Определить необходимые точки расширения (`tool`, `route` и т.д.) и требуемые права доступа (`capabilities`) в манифесте.
4. **Реализация аддона**: Написать код аддона, основываясь на утвержденных технических контрактах платформы.
5. **Параллельное тестирование**: Запустить обе реализации (в ядре и в аддоне) на одном и том же наборе поведенческих тестов.
6. **Миграция данных**: Перенести данные с верифицированной контрольной точкой. 
   - *Допустим кратковременный dual-write только для обеспечения бесшовности.*
   - *Переход должен быть атомарным (через транзакционный шлюз или строгую последовательность).*
7. **Переключение (Activation)**: Перевести активацию функции на аддон с помощью обсервабельного переключателя функций (feature switch).
8. **Окно стабильности**: Наблюдать за работой функции в продакшн-среде в течение согласованного периода.
9. **Удаление легаси**: Удалить старую реализацию, схемы, маршруты, UI-ветки и флаги только после закрытия окна стабильности.
10. **Завершение**: Пометить миграцию как завершенную после прохождения финальных проверок удаления (grep-тесты).

## 2. Сосуществование и откат

### 2.1 Правила сосуществования
- **Один записьщик**: В любой момент времени только один компонент (либо ядро, либо аддон) является авторитетным источником записи для конкретного домена.
- **Адаптеры совместимости**: Используются только для трансляции чтения/записи; они не должны содержать бизнес-логику.
- **UI-совместимость**: Легаси-UI и UI аддона могут сосуществовать, если они ссылаются на один и тот же авторитетный источник данных.

### 2.2 Правила отката (Rollback)
Откат возможен только если данные остаются читаемыми для предыдущей версии. План миграции должен включать:
- Определение того, что переносится обратно, а что остается в аддоне.
- Механизм восстановления прав доступа и секретов.
- План исправления или сброса частично перенесенных данных.

## 3. Риски и антипаттерны

### 3.1 Категорически запрещено (Anti-patterns)
- **Преждевременное удаление**: Удалять легаси-код до того, как новое решение прошло окно стабильности в продакшене.
- **Перманентная двойная запись**: Сохранять двух записьщиков для одних и тех же операционных данных после завершения миграции.
- **«Костыли» в ядре**: Добавлять специфичные литералы провайдера в ядро, чтобы «подогнать» аддон под текущую схему.
- **Иллюзия паритета**: Считать успешную установку аддона доказательством того, что функциональный паритет с легаси достигнут.

### 3.2 Основные риски и контроли

| Риск | Ранний сигнал | Метод контроля |
|---|---|---|
| Платформа разрастается вокруг реестров | Новая фича требует правки списка в ядре | Ревью точек расширения перед реализацией |
| Ядро становится God-модулем | Аддонам нужны внутренние импорты ядра | Использование только API сервисов хоста |
| Конфликты записи данных | Разный UI или дублирующие побочные эффекты | Строгое соблюдение правила одного записьщика |
| Скрытая зависимость от аддона | Запуск ядра падает без конкретного аддона | Тесты режима деградации и инертности |
| UI-раздувание | Появление веток `if (addonId === ...)` | Только дескриптивная модель вклада в UI |

## 4. Качество и верификация

### 4.1 Стратегия верификации

| Уровень | Что проверяем | Доказательство |
|---|---|---|
| **Контракты** | Схемы, совместимость, ошибки | Прохождение тестов forward-совместимости |
| **Права** | Соответствие действий правам | Матрица прав $\rightarrow$ Тесты доступа |
| **Данные** | Изоляция, бэкап, удаление | Тесты очистки и восстановления данных |
| **Runtime** | Режим деградации, бюджеты | Запуск ядра без аддонов, стресс-тесты памяти |
| **Продукт** | Поведенческий паритет | Результаты тестов характеризации (legacy vs addon) |
| **Архитектура** | Чистота границ | Grep-проверки на запрещенные импорты и литералы |

### 4.2 Критерии выхода (Exit Gates) и Git-модель
- **Проверка удаления**: Фаза миграции завершена только тогда, когда grep-проверка по удаленным путям/литералам возвращает 0 совпадений.
- **Гигиена веток**:
  - Не объединять рефакторинг ядра и изменение поведения пользователя в одном коммите.
  - Не удалять легаси в том же PR, где вводится замена. Удаление — это отдельный шаг после окна стабильности.
- **Запуск**: Продукт должен проходить `typecheck`, `lint` и запуск в среде, эквивалентной продакшн, на каждом этапе.
